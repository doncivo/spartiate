### Passe product-owner : périmètre et choix prudents

Périmètre de cette PR (consigne de la mission) : aucune partie IA (ni photo de repas, ni adaptateur), aucun client réseau Open Food Facts, aucun écran. Restent donc pour la suite : le critère 2 (appel Rust OFF, H-12), l'état « panne OFF » visible du critère 6 (écran I4-03), la photo (I4-04).

1. **Ciqual : édition 2025 (DOI 10.57745/RDMHWY), pas la 2020.** La notice data.gouv.fr de la table 2020 dit que la version de recherche.data.gouv « annule et remplace » celle-ci. Les cinq fichiers XML publiés (licence « etalab 2.0 » dans les métadonnées de l'entrepôt) sont téléchargés puis vérifiés par MD5 contre les sommes publiées ; le script `scripts/content/build-ciqual.mjs` refuse tout fichier dont la somme diffère. Aucune valeur n'est écrite à la main.
2. **Nutriments retenus** (codes Ciqual) : énergie 328 (kcal, règlement UE 1169/2011), protéines 25003 (N x 6,25, cohérent avec l'énergie 328 et les étiquettes), lipides 40000, glucides 31000, fibres 34100. Les autres nutriments (micronutriments, sel, sucres) sont I6 : hors périmètre.
3. **Valeur absente = inconnue, jamais zéro** : « - » donne `null`. Choix prudent : « traces » et « < x » donnent aussi `null` (ni zéro ni borne inventée) ; le script en publie le décompte par nutriment. Seul un « 0 » écrit par l'ANSES devient 0.
4. **Tables** : `food`, `food_portion`, `meal_entry`, `nutrition_target` (PRD § 20.2), publiées toutes les quatre (§ 9.1 : fiches perso et cache OFF, entrées, cibles). `ai_call` est I4-04. Ciqual n'a aucune ligne SQL (comme les exercices embarqués, P-09) : une entrée de journal référence `ciqual:<code>` ou l'UUID d'une fiche, et fige le nom (`food_name`) comme `exercise_name`.
5. **`meal_entry`** : colonnes explicites `kcal`, `protein_g`, `fat_g`, `carb_g` (instantané, nulles si inconnues) au lieu du JSON `macros` du § 20.2, pour la validation par colonne et la fusion champ par champ. `method` ∈ search / scan / photo / quickadd et `source` ∈ custom / ciqual / off / estimate / manual : les valeurs `photo` et `estimate` sont admises dès maintenant pour ne pas modifier le catalogue de synchro à la photo (I4-04), sans aucun flux photo ici.
6. **`nutrition_target`** : une ligne par décision, jamais modifiée (modification d'Ali = nouvelle ligne `source manual`, `accepted` ; proposition refusée = ligne `accepted = 0`, conservée pour la trace) ; la cible en vigueur est la dernière ligne acceptée dont `week_start` n'est pas dans le futur.
7. **Cache OFF** : lignes `food.source = 'off'` avec `fetched_at` publié, validité 90 jours (H-12), jamais d'index unique sur le code-barres (deux appareils hors ligne peuvent chacun créer une ligne : la plus récente gagne à la lecture, une fiche perso du même code prime). Sans client, aucune ligne OFF n'est créée ici, seul le dépôt validé et l'expiration sont fournis.
8. **Non fait, volontairement** : favoris (préférence locale : aucune colonne publiée, à décider en I4-03 avec le journal ; les récents sont calculés depuis `meal_entry`) ; complétude déclarée d'une journée (D-74 point 2 : une table non prévue au § 9.1 est un arbitrage sync-icloud / architect, jamais une ligne de ticket) ; portions de Ciqual (le fichier n'en donne pas : portions pour les fiches stockées seulement) ; micronutriments (I6).
9. **H-11 reste UNVERIFIED** : la licence est lue dans les métadonnées de l'entrepôt et consignée dans `docs/licences.md` avec l'attribution, mais aucun CONFIRMED sans constat d'Ali (D-36). H-12 inchangée (aucun appel).

### Passe relecture à froid (code-reviewer)

Défauts trouvés et corrigés avant le commit vert : 23 noms Ciqual dépassent 120 caractères (le nom figé d'une entrée est borné à 200, CHECK, catalogue de synchro et domaine alignés) ; l'aliment « moyen » du groupe 00 faisait échouer la génération (groupe `null`, aucun nom inventé) ; un caractère BOM littéral dans le script (lint) ; trois assertions non nulles dans un test ; une affectation inutile ; un `afterEach` qui fermait une base jamais ouverte.

Points laissés à la relecture indépendante (sync-icloud, code-reviewer) :

1. Les CHECK numériques (bornes de macros, grammes > 0) ne sont pas reflétés par le catalogue de synchro (type `real`) : une ligne reçue hors bornes, d'un appareil défectueux, ferait échouer son application. Même risque que les CHECK existants ; les listes fermées sont, elles, reflétées par `values`.
2. Deux lignes OFF du même code (deux appareils hors ligne) coexistent ; la lecture départage, aucune purge des doublons. `expireOffCache` supprime logiquement une ligne dont la suppression est ensuite publiée : un autre appareil qui l'avait rafraîchie entre-temps la verrait supprimée (champ `deleted_at` en conflit avec `fetched_at`, fusion par champ).
3. `recentFoods` utilise une sous-requête corrélée (index `idx_meal_entry_food`) : adaptée à un journal personnel, non mesurée sur de gros volumes.
4. 145 aliments Ciqual n'ont pas d'énergie 328 : leur total du jour sera « inconnu » (jamais 0). Substituer l'énergie 333 est une décision d'Ali ou de content-data, non prise ici.
5. Le titre des conflits (`titleSource`) des entrées de journal est le nom de l'aliment : donnée locale du journal des conflits, jamais écrite dans `applog` (à confirmer par sync-icloud / security-privacy).
