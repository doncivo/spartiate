## Passe data-model : conception retenue

### Où l'ancien identifiant peut exister (inventaire)

| Emplacement | Peut le porter ? | Traitement |
| --- | --- | --- |
| `settings` `training.activeEquipmentProfile` (local, jamais publié ni exporté, effacé par « Repartir de zéro ») | oui | `UPDATE` de la migration 0022 + lecture tolérante |
| `settings` `onboarding.draft`, `onboarding.answers` (locaux, objets bruts lus par `parseDraft`) | oui (`equipmentProfileId`) | `json_set` de la migration 0022 + `parseDraft` |
| `equipment_profile` (publiée) | **non** : identifiant UUID imposé par le dépôt (`isId`) ; les profils embarqués ne sont pas des lignes (copie personnelle = nouvel UUID) | rien à migrer ; aucune ligne n'est renommée (changer la clé d'une ligne publiée serait une suppression et une création) |
| `routine`, `routine_day`, `routine_exercise`, `workout` | non : aucune colonne ne référence un profil de matériel | rien |
| Programmes `content/programs/*.json` (`compatibleProfileIds`) | oui | renommés (contenu embarqué, relu à chaque démarrage) |
| Export complet / archive (D-57) | non : seul `ui.theme` est exporté des réglages ; les lignes `equipment_profile` ont un UUID | rien (archives de schéma ≤ 21 lues sans changement) |
| Journaux de synchro, instantanés, `sync_unknown`, `sync_parked` | non : le profil actif n'est pas publié ; `equipment_profile` porte des UUID | rien |

Une ligne `equipment_profile` reçue ou importée avec l'ancien identifiant n'est donc pas un cas atteignable (aucun chemin d'écriture ne la produit) ; si elle existait, elle resterait une copie personnelle à part, sans effet sur l'embarqué. Les références, elles, sont toutes rattachées au nouveau (migration + lecture).

### Forme retenue pour l'ancien identifiant

Il n'existe QUE dans `src/db/migrations/0022_default_profile_rename.ts`, reconstruit par codes de caractères : `'fitness-park-'` + `String.fromCharCode(...)` pour les tests, `'fitness-park-' || char(...)` dans le SQL. Pourquoi pas une empreinte : la migration est du SQL sans paramètre (une empreinte n'est pas comparable en SQL), et le jeu de migrations est exporté en JSON pour les tests Rust (`spartiate-migrations.json`) : le texte du lieu n'apparaît donc ni dans le source, ni dans ce JSON, ni dans le bundle lisible. Aucun module de domaine : un module de plus au départ coûtait des octets (voir mesure), et une lecture tolérante est inutile (profil actif inconnu = profil par défaut ; brouillon et réponses migrés). La garde `privacy.test.ts` détecte le nom par l'empreinte SHA-256 de chaque mot (découpage aux non-lettres et aux majuscules internes : `FOO_NOM`, `fooNom`, `d'Nom`) et des chemins : la liste de codes n'est pas un mot, la garde reste verte sans exception pour ce fichier.

### Migration 0022 (`0022_default_profile_rename.ts`, schéma 22)

Un seul `UPDATE` sur `settings` (locale, sans déclencheur) : `replace(value, '"<ancien>"', '"salle-complete"')` pour les clés `training.activeEquipmentProfile`, `onboarding.draft` et `onboarding.answers` (texte JSON entre guillemets : valeur entière ou champ d'un objet ; valeur illisible ou sans l'ancien identifiant inchangée). Ni `updated_at`, ni `hlc` ne sont touchés (réglages locaux, jamais publiés : l'horodatage n'a aucun effet). Aucune table, aucun index, aucun déclencheur : `REFERENCE_TRIGGERS` inchangé (116). Sauvegarde avant migration par le migrateur (existant). `APP_SCHEMA_VERSION` = 22, `spartiate-migrations.json` régénéré, `identity.test.ts` et `training_schema.rs` alignés.

### Appareil resté en 0.29.1 (schéma 21)

Rien de ce lot n'est publié : le profil actif est un réglage local, les profils embarqués ne sont pas des lignes, aucune table ni colonne publiée n'est ajoutée. Un appareil en 0.29.1 ne reçoit donc **jamais** « salle-complete » par la synchro et ne perd rien. Les écritures d'un appareil en 0.29.2 portent `sv` = 22 et les mêmes tables et colonnes qu'en 21 : le lecteur 0.29.1 les applique normalement (aucun champ ni table inconnu, donc ni `sync_unknown` ni `sync_parked`) ; le `sv` supérieur n'est signalé que comme information de version plus récente (`newerKind` = `schema`, ni majeure, donc lecture non suspendue). ADR 0018 (ligne créée par un schéma plus ancien) ne s'applique pas : la 0.29.2 n'ajoute aucune colonne. Si une base de schéma 22 était restaurée dans une 0.29.1, `restore_hardening` la refuse (version supérieure à `APP_SCHEMA_VERSION`), sans perte. Si, par un chemin hors synchro, une 0.29.1 lisait `salle-complete` comme profil actif, `resolveActiveProfile` retombe sur son profil par défaut embarqué (même matériel).
