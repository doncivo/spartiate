## Passe product-owner : critères

### IOS-029a — verrou Face ID / code (iPhone seulement)

Le verrou est entièrement codé depuis I-03 (`src/domain/appLock.ts`, `src/features/security/**`, `src/platform/biometric/**`, plugin
officiel `tauri-plugin-biometric` =2.4.1, cache `privacy-shield`) ; seule la ligne de réglage était masquée (`__ctShowAppLockRow`, D-37).

- C-a1 (réglage visible, désactivé par défaut) — Given l'iPhone (authentification prise en charge), When Plus s'ouvre, Then la ligne
  « Verrouillage Face ID » (libellé selon l'état : biométrie, code de l'iPhone) est visible, interrupteur désactivé sur une installation
  neuve (`security.appLock` absent → désactivé, `parseAppLockSetting`) ; aucun drapeau de test ne la conditionne plus.
- C-a2 (activation authentifiée) — Given le réglage désactivé, When Ali l'active, Then Face ID est demandé (raison « Activer le
  verrouillage de Spartiate », repli code `allowDeviceCredential: true`) ; refus, annulation ou indisponibilité : rien n'est activé et le
  message « Le verrouillage n'a pas été activé » (+ cause : aucun code, indisponible) est affiché (déjà couvert : `startAppLock.test.tsx`,
  `appLockQa.test.tsx` ; prouvé ici par un test de l'écran).
- C-a3 (verrouillage) — Given le verrou activé, When l'app est lancée, ou revient au premier plan après 30 s ou plus en arrière-plan,
  Then l'écran de verrou couvre tout jusqu'à Face ID réussi ou repli sur le code de l'iPhone (`deviceOwnerAuthentication`) ; aucun contenu
  visible derrière (couche opaque + `privacy-shield` dans le sélecteur d'apps). Délai : 30 s, fixe (I-03 D1, `APP_LOCK_RELOCK_MS`,
  décision proposée ci-dessous) ; excursions voulues par l'app (sélecteur, caméra, autorisation) < 5 min : pas de verrou.
- C-a4 (jamais sur le PC) — Given le PC, When Plus ou Réglages s'ouvre, Then aucune ligne de verrou n'existe et l'app ne se verrouille
  jamais (`authenticator.supported = false` hors iPhone ; `SettingsScreenPc` ne monte pas `SecuritySection`).
- C-a5 (texte d'usage) — Given `Info.ios.plist`, Then `NSFaceIDUsageDescription` est présent, en français, propre à Spartiate (l'ancien
  texte parlait de « tâches », reliquat de CircleTasks) ; contrat plist vert.
- C-a6 (matrice) — la ligne H-17 de `docs/capability-matrix.md` passe de DEFERRED à UNVERIFIED (activation autorisée sur l'iPhone),
  jamais CONFIRMED avant le constat d'Ali.

### IOS-029b — essai Apple Intelligence (spike sans engagement)

- C-b1 (plugin) — plugin Swift local `apple-intelligence` (crate `tauri-plugin-apple-intelligence`), une méthode `probe` : texte
  SYNTHÉTIQUE fixe écrit dans le Swift (aucun argument : aucune donnée de l'app, encore moins corporelle, ne peut y entrer), réponse ou
  erreur rendues telles quelles (tronquées : réponse 2 000, description 300 caractères). `#if canImport(FoundationModels)` et
  `@available(iOS 26.0, *)` : SDK ancien → `sdk-absent`, iOS < 26 → `os-too-old`, jamais un échec de build.
- C-b2 (pont) — Rust seul appelle le plugin (`src-tauri/src/apple_intelligence.rs`, commande `apple_intelligence_probe`, délai 60 s par
  `mobile_call.rs`), capability `apple-intelligence-ios.json` à liste exacte, iPhone seulement ; aucune commande sur PC.
- C-b3 (façade) — `src/platform/appleIntelligence` : adaptateur iPhone, stub Windows `unsupported`, faux pour les tests ; toute réponse
  de forme inattendue ou erreur d'appel → résultat `failed` avec le code, jamais une exception.
- C-b4 (écran) — Plus › Logs (diagnostic) › Outils de test › « Essai Apple Intelligence » : bouton « Lancer l'essai », puis le texte
  envoyé, la réponse du modèle ou le motif d'indisponibilité / l'erreur telle quelle ; PC : « indisponible sur cet appareil ». Chargé à la
  demande avec l'écran des Logs (hors du départ), textes dans `src/i18n/fr.appleIntelligence.ts`.
- C-b5 (hypothèse) — H-41 proposée (registre provisoire, PRD § 26.2 figé) et ligne UNVERIFIED dans `docs/capability-matrix.md`.

Hors périmètre : toute utilisation du modèle dans une fonction de l'app (bilan, import, repas) ; tout envoi de donnée de l'app au modèle.

## Décisions proposées (sans numéro, à numéroter par l'appelant)

1. Verrou iPhone : délai de reverrouillage gardé à 30 s fixe (I-03 D1) plutôt qu'« immédiat » ou « 1 min » ; aucun réglage de délai.
2. Verrou PC : réglage absent du PC (ni ligne grisée ni « disponible sur iPhone ») ; Windows Hello reste hors lot.
3. Texte d'usage Face ID : « Spartiate utilise Face ID pour verrouiller l’app à l’ouverture. » (relecture security-privacy).
4. H-41 : « Le modèle local d'Apple (Foundation Models, iOS 26) répond à Spartiate installée par SideStore (Apple ID gratuit) sur
   l'iPhone 16 Pro Max », UNVERIFIED, preuve : capture d'Ali de l'essai (réponse ou erreur).
5. Essai Apple Intelligence : plugin séparé `apple-intelligence` (plutôt qu'une commande ajoutée à un plugin existant, aucun n'ayant le
   même objet) ; texte fixe dans le Swift.

## Constats d'Ali à faire (iPhone installé par SideStore, après le build du lot)

1. Plus : ligne « Verrouillage Face ID » visible, désactivée ; l'activer : Face ID demandé ; refuser une fois : rien n'est activé, message.
2. Activé : fermer puis rouvrir l'app → écran de verrou ; Face ID → déverrouillé ; annuler Face ID puis « Déverrouiller » → repli code.
3. Retour au premier plan après plus de 30 s → verrou ; après moins de 30 s → pas de verrou ; sélecteur d'apps : rien de lisible.
4. Plus › Logs › Outils de test › « Essai Apple Intelligence » → « Lancer l'essai » : capture de la réponse ou de l'erreur affichée.

## Relecture security-privacy proposée

Texte d'usage Face ID nouveau ; aucun entitlement ni clé plist nouveaux pour Foundation Models (vérifier sur le binaire signé :
`codesign -d --entitlements :-` inchangé) ; texte envoyé au modèle fixe et synthétique ; réponse affichée seulement, jamais enregistrée
ni journalisée (rien n'est écrit au journal technique).

## Passe qa-test : cas limites

- Verrou : réglage illisible → verrouillé (échec fermé) ; aucun code défini → activation refusée sans fenêtre Face ID ; biométrie refusée
  mais code défini → libellé « code de l'iPhone » et activation par le code ; Touch ID → libellé générique (tests existants
  `startAppLock.test.tsx`, `appLockQa.test.tsx`, `AppLockGate.test.tsx`, ce dernier passé en mise en page iPhone : la ligne n'existe plus
  dans le panneau PC « À propos et diagnostic »).
- PC : même avec une authentification injectée, aucune ligne (`SettingsPc.test.tsx`) ; `SecuritySection` retiré de `SettingsPanels.tsx`.
- Essai : deux appuis rapides → bouton désactivé pendant l'essai ; écran quitté pendant l'essai → résultat ignoré ; Swift muet → délai
  Rust 60 s, `appleintelligence-timeout` affiché ; réponse de forme inattendue → `bad-reply` ; motif inconnu du système → « le système
  n'a pas dit pourquoi » avec le détail brut ; réponse et description tronquées (2 000 / 300).

## Passe code-reviewer

- Swift : chaque chemin résout (aucun `reject`), aucun argument lu, aucun réseau ni stockage (test statique) ; `Invoke` capturé dans un
  `Task` comme `LiveActivityPlugin` (mode Swift 5). Risque non vérifiable sans Mac : nom exact des surcharges `respond(to:)` et forme de
  `availability` dans le SDK de la CI ; si la compilation échoue, retirer le plugin du build n'est pas nécessaire : remplacer le corps de
  `ask()` par le motif `sdk-absent` et consigner (l'écran dit alors « indisponible »).
- Chargement faible du framework sous iOS < 26 : attendu par les références faibles de Swift (`@available`), non prouvé ; l'iPhone d'Ali
  est sous iOS 26 ou plus (à confirmer avec le constat).
